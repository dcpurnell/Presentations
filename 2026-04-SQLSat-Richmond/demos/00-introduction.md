## SQL Saturday Richmond: Vector Embeddings with Ollama

Let's start with a question: how do you search text in SQL Server today?
You've got two tools in the box — LIKE and Full-Text Search.

**LIKE is exact pattern matching.**

```sql
WHERE description LIKE '%performance%'
```

It works, but you need to know the EXACT words. Leading wildcards (`'%perf%'`)
kill your indexes and force table scans. We've all been there.

**Full-Text Search is better** — `CONTAINS(description, 'performance OR optimization OR tuning')`
It understands word forms automatically ("optimizing" matches "optimize") and can
support synonyms, but you have to configure those manually.

Here's what BOTH have in common: they're looking for exact words or
known variations. Neither one understands MEANING or INTENT.

Think about how people search today. Nobody types exact keywords anymore.
They type natural language: "How do I make my database queries run faster?"
That should match articles like:

* "Best practices for SQL Server query optimization"
* "Index tuning strategies for better performance"
* "Reducing execution time with efficient query design"

Zero overlapping keywords between the search and those descriptions —
but the MEANING is the same.

In our world at Elon, imagine a student searching the course catalog:
"I want to learn about making decisions with data"
That should find "Introduction to Business Analytics" and
"Statistical Methods for Decision Making" even though the words
don't match at all.

This is the **VOCABULARY MISMATCH** problem. Users search with intent and
personas — "I want to work with data" — but catalogs describe features:
"Provides foundational skills in statistical modeling and interpretation."
Same meaning, zero overlapping words. A student searching for their
career goal won't use the language of a course description.

This is the semantic search problem. Traditional SQL search can't do this.
SQL Server 2025 can. That's what we're here to talk about.

### Additions to SQL Server 2025

* VECTOR data type for storing embeddings (up to 1,998 dimensions
    with float32, 3,996 with float16)
* CREATE EXTERNAL MODEL for registering models (Ollama, OpenAI, etc)
    in SQL Server
* AI_GENERATE_EMBEDDINGS function to create vector representations of
    text using Ollama models
* VECTOR_DISTANCE function for calculating similarity between vectors
* VECTOR_SEARCH function for efficient approximate nearest neighbor
    search using DiskANN indexes
* DiskANN vector indexes for fast similarity search on large datasets

Mala Mahadevan put it best at SQL Saturday Atlanta:
**"This feature is 20% AI and 80% math."**
Embeddings are just arrays of numbers. Distance calculations are
just math. The AI part is the model that converts text to numbers.
Everything else is pure SQL Server.

Before we can do any of this, we need two things: SQL Server 2025
and an embedding model. I'm using Docker for SQL Server and Ollama
for the local LLM.

### Why Ollama?

* Privacy, lab, and POC.

The challenge with Ollama is having the GPUs to run it. It's not a
hosted API like OpenAI — you have to run it yourself.
But if you can run it, it's fantastic for local development
and testing. It supports all the same models as OpenAI, but
runs on your own machine with no latency and no data leaving your
environment. Perfect for demos and POCs.

I'm using Anthony Nocentino's docker-compose stack — it bundles
everything: SQL Server 2025, Ollama, nginx proxy, SSL certs.
Three commands and you're up.

<https://github.com/nocentino/ollama-sql-faststart>

* `git clone https://github.com/nocentino/ollama-sql-faststart.git`
* `cd ollama-sql-faststart`
* `docker compose up --detach`

The architecture challenge: SQL Server 2025 only calls HTTPS endpoints
for external models. Ollama only listens on HTTP. Solution: nginx
sits in the middle as a reverse proxy doing TLS termination.

```text
SQL Server → HTTPS → nginx → HTTP → Ollama
```

The self-signed cert generated by the config container gets
volume-mounted into SQL Server so it trusts the proxy automatically.
No manual cert trust steps.

## LLMs and Retrieval-Augmented Generation (RAG)

<https://azure.microsoft.com/en-us/resources/cloud-computing-dictionary/what-is-retrieval-augmented-generation-rag>

### Why RAG Exists — The LLM Knowledge Gap

Large language models are trained on a snapshot of data, they
have a knowledge cutoff date. They don't know about your course
catalog, your student records, your institution's policies. They
can't answer "which elective pairs well with Data Structures?"
because they've never seen your data. Fine-tuning is expensive
and static. RAG is the practical solution: instead of retraining
the model, you *retrieve* relevant context at query time and feed
it to the LLM alongside the question.

### The Two-Step RAG Process

RAG is deceptively simple, it's just two steps: retrieve, then
generate. Step 1: take the user's question, convert it to a
vector, search your vector store for semantically similar
content, and pull back the top K results. Step 2: stuff those
results into the LLM's prompt as context and let it generate an
answer grounded in your actual data. The LLM becomes a reasoning
engine over *your* content rather than its training data.

### Vector Search IS the Retrieval Layer

This is the critical connection, vector search isn't just
*related* to RAG, it *is* the retrieval mechanism. When someone
asks "what courses help with data science careers?", the vector
search finds courses like Statistical Methods, Machine Learning
Fundamentals, and Data Visualization — not because those words
appear in the query, but because the *meaning* aligns. Without
vector search, you're back to keyword matching, and keyword
matching can't bridge the vocabulary gap between how users ask
questions and how your content describes itself.

### If Retrieval Fails, RAG Fails

If your vector search returns irrelevant courses, the LLM will
confidently generate a wrong answer based on those irrelevant
courses. The LLM has no way to know the retrieval was bad — it
trusts whatever context you give it. You can swap in GPT-4,
Claude, Llama — doesn't matter. If the retrieval layer hands back
garbage, the most sophisticated LLM in the world will produce a
polished, articulate, wrong answer. The quality ceiling of your
entire RAG application is determined by the quality of your
vector search which is determined by the quality of your data.

### Why This Matters for Your SQL Server Investment

Every vector concept in this presentation — choosing the right
embedding model, understanding cosine distance, building DiskANN
indexes, tuning VECTOR_SEARCH parameters, these aren't academic
exercises. They're the foundation that determines whether your
RAG application actually works. When you get vector search right
in SQL Server, you're not just running similarity queries —
you're building the retrieval layer that powers AI applications
over your own data, inside your existing security model, without
sending your data to external vector databases.
